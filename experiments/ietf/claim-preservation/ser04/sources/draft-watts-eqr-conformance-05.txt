    Deterministic Conformance Profile and Test Vectors for Evidence
                         Qualification Receipts
                     draft-watts-eqr-conformance-05

Abstract

   This document defines a deterministic conformance profile and test-
   vector corpus for Evidence Qualification Receipts (EQRs).  The
   profile, named eqr-core-1, makes receipt conformance mechanically
   reproducible: strict JSON structure, SHA-256 digest encoding, UTC
   timestamp handling, evidence-reference integrity, requirement-state
   derivation, and three-valued PASS, FAIL, or INDETERMINATE results are
   checked by a closed algorithm.  The profile is intentionally narrow.
   Conformance does not establish that evidence is true, that a
   proposition is scientifically valid, that an issuer is trustworthy,
   or that an action is authorized.  The goal is interoperable
   verification of receipt semantics, not promotion of conformance into
   substantive truth.

1.  Introduction

   Evidence Qualification Receipts are described in [I-D.watts-eqr].
   Their central requirement is that unresolved required evidence remain
   distinguishable from both satisfied and failed evidence, and that
   qualification remain distinct from authorization.  That architectural
   distinction is useful only if independent implementations derive the
   same status from the same declared requirement states.

   This document therefore defines a strict conformance profile, eqr-
   core-1, plus executable test vectors.  The profile does not attempt
   to determine whether evidence corresponds to reality.  It determines
   whether an EQR object is structurally and semantically self-
   consistent under a fully specified finite rule set.

   A receipt can be conformant and still contain evidence from an issuer
   a relying party does not trust.  A conformant PASS result is not
   permission to execute an action.

2.  Conventions and Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Conformance  Agreement with the finite syntactic and semantic rules
      of this profile.

   Substantive validity  Whether the underlying evidence and proposition
      are actually correct.  This document does not establish it.

   Requirement state  One of satisfied, failed, missing, unresolved, or
      stale.

   Derived status  The PASS, FAIL, or INDETERMINATE result computed from
      the requirement states.

3.  The eqr-core-1 Profile

   An eqr-core-1 object is a JSON object as defined by [RFC8259].
   Duplicate JSON member names MUST cause non-conformance.

   SHA-256 is the only digest algorithm in this profile [RFC6234].
   Digest values MUST be exactly 32 octets represented using unpadded
   base64url [RFC4648].  A producer that hashes a JSON object MUST first
   apply the JSON Canonicalization Scheme [RFC8785].

   All timestamps in this profile MUST be UTC Internet timestamps ending
   in Z and conforming to [RFC3339].

3.1.  Required Members

   The profile requires exactly the following top-level members:

   *  version, whose value is "1";

   *  profile_id, whose value is "eqr-core-1";

   *  receipt_id and issuer;

   *  issued_at, expires_at, and evaluation_time;

   *  profile and claim SHA-256 digest objects;

   *  requirements;

   *  evaluation;

   *  evidence; and

   *  supersedes, which can be null.

   The strict member set is intentional for this conformance profile.
   Other EQR profiles can define extensions.

3.2.  Requirement States

   Each requirement has a unique id, one state, and an optional array of
   evidence_ids.  The only states are:

   *  satisfied;

   *  failed;

   *  missing;

   *  unresolved; and

   *  stale.

   A satisfied requirement MUST name at least one evidence object.
   Every named evidence identifier MUST resolve within the same receipt.
   Evidence used by a satisfied requirement MUST NOT be stale at
   evaluation_time.

4.  Deterministic Status Derivation

   The status derivation function is:

   def derive_status(requirements):
       if not requirements:
           return "indeterminate"

       states = [r["state"] for r in requirements]

       if any(s == "failed" for s in states):
           return "fail"

       if all(s == "satisfied" for s in states):
           return "pass"

       return "indeterminate"

   FAIL has precedence over missing or unresolved information.  PASS is
   possible only for a non-empty requirement set in which every
   requirement is satisfied.  In every other valid case the result is
   INDETERMINATE.

   The receipt's declared evaluation.status MUST equal the derived
   status.  A mismatch is non-conformant; a verifier MUST NOT rewrite
   the declaration to make it conform.

5.  Time and Freshness Rules

   expires_at MUST be later than issued_at.  evaluation_time MUST fall
   within the inclusive receipt validity interval.

   An evidence object has a fresh_until timestamp.  A requirement
   declared satisfied is non-conformant if any evidence object it relies
   on has fresh_until earlier than evaluation_time.

   This rule checks self-consistency only.  It does not establish that
   the chosen freshness interval is appropriate for a relying party's
   risk or policy.

6.  Deterministic Processing Order

   An implementation can perform checks in any internal order, but its
   externally observable result MUST be equivalent to the following
   logical sequence:

   1.  strict JSON parsing, including rejection of duplicate member
       names;



Watts                      Expires 3 May 2027                   [Page 5]

Internet-Draft               EQR Conformance                October 2026


   2.  top-level and nested shape validation;

   3.  profile, version, digest, and timestamp validation;

   4.  evidence identifier and freshness validation;

   5.  requirement-state and evidence-reference validation;

   6.  deterministic status derivation;

   7.  declared-status equality check; and

   8.  supersession self-reference check.

   A later semantic check MUST NOT convert an earlier non-conformant
   input into a conformant qualification result.  Implementations can
   report diagnostics from the earliest detected error or aggregate
   diagnostics, but they must agree on the conformance Boolean and, for
   conformant inputs, the derived status.

7.  Append-Only Supersession

   supersedes can identify a predecessor receipt.  It MUST NOT equal the
   current receipt_id.  This profile does not mutate predecessor state.
   New evidence is represented by a new receipt.

8.  Conformance Outcome

   A verifier returns two logically separate outputs:

   *  *conformant*: whether the object satisfies this profile; and

   *  *derived_status*: pass, fail, or indeterminate when the object is
      conformant.

   Non-conformance MUST NOT be reported as PASS, FAIL, or INDETERMINATE.
   Those values describe evidence qualification semantics, not parser or
   profile validity.

9.  Deterministic Verifier Result

   A verifier implementation claiming eqr-core-1 semantic conformance
   MUST expose, directly or through an equivalent API, the following
   logical result:







Watts                      Expires 3 May 2027                   [Page 6]

Internet-Draft               EQR Conformance                October 2026


   {
     "profile_id": "eqr-core-1",
     "conformant": true,
     "derived_status": "pass"
   }

   conformant is a Boolean.  derived_status is one of pass, fail, or
   indeterminate only when conformant is true.  For a non-conformant
   object, a verifier MUST NOT assign a qualification status; the
   logical value of derived_status is null or absent.

   Implementations MAY expose additional diagnostic reason codes.
   Diagnostic strings are not evidence status and are not part of the
   qualification lattice defined by this document.

10.  Conformance Claim Levels

   To prevent overbroad or false-positive conformance claims, this
   document distinguishes four claim levels.  An implementation MUST NOT
   claim a stronger level merely because a weaker level has passed.

   Syntax Conformance  The input is accepted under the strict JSON and
      field constraints of this profile.

   Semantic Conformance  The implementation derives PASS, FAIL, and
      INDETERMINATE exactly as specified and enforces the evidence-
      reference, time, digest, and supersession rules.

   Vector-Profile Conformance  The implementation produces the expected
      conformance Boolean and derived status for every normative vector
      identified by the declared vector-corpus digest.

   Independent Reproduction  A separately implemented verifier, under
      independently controlled source and execution conditions,
      reproduces the declared vector-profile results.  Running two code
      paths in the same package or environment is not sufficient by
      itself.

   Syntax Conformance does not imply Semantic Conformance.  Semantic
   Conformance does not imply complete Vector-Profile Conformance.
   Complete Vector-Profile Conformance does not imply Independent
   Reproduction.

11.  Conformance Claim Report

   A published claim of complete Vector-Profile Conformance SHOULD
   identify:

   *  the profile identifier;

   *  the exact SHA-256 digest of the vector corpus;

   *  the implementation name and version or source digest;

   *  the execution environment sufficient to reproduce the test;

   *  the number of vectors attempted, passed, and failed; and

   *  whether the result is local execution evidence or independent
      reproduction.

   A report MUST NOT omit failed vectors while claiming complete vector-
   profile conformance.  A report for a different vector-corpus digest
   is a different conformance claim.

   {
     "profile_id": "eqr-core-1",
     "vector_corpus_sha256":

       "name": "example-verifier",
       "version": "1.0"
     },
     "execution": {
       "attempted": 21,
       "passed": 21,
       "failed": 0,
       "independent_reproduction": false
     }
   }

   The example report is non-normative.  In particular, setting
   independent_reproduction to true is a provenance assertion that
   requires evidence external to the conformance algorithm itself.

   The companion corpus contains twenty-one vectors covering valid PASS,
   FAIL, and INDETERMINATE cases plus malformed or internally

   The corpus includes empty requirements, FAIL precedence, missing and
   stale evidence, duplicate requirement identifiers, a raw JSON
   duplicate-member case, unsupported hash algorithms, invalid digest
   encodings, expired receipts, unknown evidence references, invalid

14.  Falsifiability and Limits

   This specification is intentionally falsifiable at the implementation
   layer.  If two purportedly conformant implementations produce
   different outputs for the same normative vector, at least one
   implementation is non-conformant or the specification is ambiguous
   and requires revision.

   Passing all vectors does not establish truth of the evidence,
   scientific validity of the proposition, honesty of the issuer,
   appropriateness of the profile, authorization to act, successful
   execution, or safety.  Those are different claims requiring different
   evidence.

   A single normative vector for which a claimed complete Vector-Profile
   Conformance implementation produces the wrong conformance Boolean or
   wrong derived status is a sufficient counterexample to that
   implementation's complete conformance claim.  A single independently
   reproduced disagreement between reasonable implementations can also
   indicate an ambiguity in this specification and should be treated as
   a specification defect until resolved.

15.  Relationship to Other Work

   This document is a conformance companion to [I-D.watts-eqr] and
   follows the non-collapse distinction described in
   [I-D.watts-noncollapse].  It does not replace executor-side action/

   conformance receipts such as [I-D.correctover-ccs].

16.  Changes from -01

   Revision -02 keeps the eqr-core-1 data model, status lattice, and
   normative vector-corpus digest unchanged.  It adds explicit
   conformance claim levels, a canonical logical verifier result, a
   reproducible conformance-claim report, and deterministic processing-
   order requirements.  These additions are intended to prevent a
   parser-only success, partial vector run, or same-environment cross-
   check from being presented as complete or independently reproduced
   conformance.

   Revision -02 also refreshes the informative Correctover CCS citation
   to revision -10.  No scientific truth, authorization, issuer trust,
   or independent-reproduction claim is added by this revision.

18.  Conformance Manifest and Execution Evidence

   A vector-profile conformance claim MUST identify the exact vector
   corpus SHA-256 digest, profile identifier, implementation source or
   binary digest, runner identity, runtime and operating-system
   versions, invocation, UTC execution time, attempted-vector count,
   pass count, fail count, and individual vector outcomes.  A claim MUST
   NOT assert complete vector-profile conformance if any normative
   vector was skipped, omitted, or failed.  The manifest is an evidence
   record, not a cryptographic attestation unless independently signed
   and authenticated.

   The report's independent_reproduction field MUST be false unless the
   claimant has separately documented independent control of the
   implementation, test execution, and signing keys, if any.  A self-
   declared true value is not proof of independence.

19.  Independent Reproduction Protocol

   Independent reproduction requires an implementer other than the
   original author to acquire the normative corpus with its expected
   digest, implement the specified rules without copying the supplied
   verifier, execute all vectors in an independently controlled
   environment, and report per-vector outcomes and environment
   provenance.  The reviewer SHOULD derive expected outputs from the
   specification before consulting the corpus answers.  The reviewer
   MUST distinguish independently obtained results from copied reference
   outputs.

   Disagreement on the conformance Boolean or on the derived status of a
   conformant object is a reproducible counterexample to at least one
   implementation's claim, or evidence of specification ambiguity.
   Diagnostic strings and the order of diagnostic discovery are non-
   normative and need not match.

20.  Negative Tests and False-Positive Resistance

   Complete vector-profile claims include both expected-conformant and
   expected-nonconformant cases.  Negative tests cover duplicate JSON
   member names, invalid encodings, unknown evidence references, expired
   receipts, stale supporting evidence, missing requirements,
   contradictory declared status, and unauthorized promotion of an
   INDETERMINATE result to PASS.  A test runner MUST count rejection of
   an expected-invalid input as a successful negative test; it MUST NOT
   count acceptance of such an input as success.

   Every vector's expected conformance Boolean and derived status are
   compared independently.  An expected-nonconformant input has no
   derived qualification status; a diagnostic reason string is
   informative only.

21.  Append-Only Corrections and Reproducibility History

   A corrected receipt or execution report is a new record with a new
   identifier and a reference to its predecessor.  Producers MUST NOT
   silently overwrite or relabel the original record when presenting a
   historical verification chain.  A receipt's supersedes field remains
   governed by the frozen eqr-core-1 rules; this section adds no new
   validation condition to the core profile.

22.  Additional Security and Misrepresentation Considerations

   A forged or replayed conformant receipt can satisfy the syntax and
   semantic profile while being untrustworthy or unauthorized.  A
   relying party must independently apply issuer authentication, anti-
   replay policy, evidence trust, revocation, and action authorization
   as appropriate.  Digest equality is not proof of issuer identity or
   provenance.  Expiration and freshness checks are local self-
   consistency conditions, not a complete replay defense.

   Reviewers should treat unverified claims of independently controlled
   implementations, signing keys, or test infrastructure as
   unsubstantiated.  Conformance and independent reproduction are
   distinct from empirical validation and operational safety.

23.  Changes from -02

   Revision -03 adds a conformance-manifest reporting template,
   independent reproduction protocol, negative-test completeness rules,
   append-only correction guidance, and additional replay/forgery/
   misrepresentation analysis.  It does not change the eqr-core-1
   schema, deterministic status derivation, or normative test-vector
   corpus digest.

24.  Security Considerations

   Strict parsing prevents duplicate-member substitution and status
   laundering through ambiguous JSON.  Digest and timestamp checks
   prevent several classes of malformed or stale self-consistency
   claims, but this profile provides no key management, issuer
   authentication, revocation, trust-anchor selection, or policy
   decision.

   A malicious issuer can create a perfectly conformant receipt
   containing false evidence.  Therefore conformant MUST NOT be
   interpreted as truthful, trusted, authorized, or safe.

25.  Privacy Considerations

   Evidence identifiers and digests can still act as correlators.
   Implementations should minimize externally exposed evidence metadata
   and avoid placing sensitive plaintext into receipts when a scoped
   digest or protected reference is sufficient.

27.  Supplemental Negative-Test Resistance and Bounded Failure

   An eqr-core-1 verifier is not permitted to promote malformed
   structures, unknown evidence, or contradictory states to a successful
   qualification.  The corresponding conformance outcome for a non-
   conformant input has no derived qualification status.  An unhandled
   parser or type exception does not count as a successful negative-test
   rejection in operational conformance reports.

   This revision provides a separate, non-normative supplemental
   adversarial corpus with 15 tests, including unhashable identifiers,
   malformed references, and non-JSON numeric constants.  It does not
   replace or change the frozen 21-vector normative corpus identified in
   Section 12, and no previous local or independent outcome is inferred
   from these new cases.

   The SHA-256 digest of the accompanying development test corpus, eqr-
   negative-supplement-v0.1.json, is:

   a8d53b68bd9373d4ab94c0d5728909991492ff88615ca813bbd609e06d9a134b

   Implementers SHOULD reject unhashable identifier and evidence-
   reference values cleanly and record the counterexample, rather than
   raising an uncaught exception that prevents a complete report.
   Negative tests are satisfied only if the verifier rejects input and
   does not assign PASS, FAIL, or INDETERMINATE; this is a conformance-
   model test, not a demonstration that the supplied evidence is true or
   an action is authorized.

28.  Changes from -03

   Revision -04 retains the full -03 specification and references and
   leaves the eqr-core-1 wire format, status lattice, and frozen
   normative vector digest unchanged.  It adds the bounded-failure
   discussion and a separately identified non-normative negative test
   supplement.  RFCXML author metadata and citation context are
   preserved from the author-held nits-fixed -03 source; root
   submissionType is omitted to avoid claiming a stream absent in the
   Datatracker record, and the document date reflects this staging
   exercise.  This is a candidate for review and not an approved
   submission.
