       Citing Signed Evaluation Receipts from Existing Envelopes
              draft-gruszka-evaluation-receipt-mappings-04

Abstract

   A Signed Evaluation Receipt records one evaluation result as signed
   payload bytes B.  This document describes how existing envelopes cite
   such a receipt by the SHA-256 digest of B, and how a DSSE envelope
   carries B with the receipt's own signature.  It fixes those bytes and
   a matching rule, maps the parts of a receipt onto DSSE, the in-toto
   Statement with the test-result predicate and the SLSA Verification
   Summary Attestation, shows that the signature of a receipt is already
   a valid DSSE signature, gives a SCITT Signed Statement that names a
   receipt only by its digest, in a key profile and a certificate
   profile, declares the receipt digest as an artifact type for typed
   digest references, states how three formats for records of agent
   actions can cite a receipt, and relates a receipt to a pre-run
   criteria set written in PRML.  It defines no new format and no new
   predicate.

1.  Introduction

   A Signed Evaluation Receipt (receipt) [RECEIPTS] holds one assertion,
   whether a threshold held for a metric of a test suite, as payload
   bytes B.  B is signed with Ed25519 over a pre-authentication encoding
   with a fixed type.  A receipt carries no inclusion proof and does not
   prove registration with a Transparency Service.  In SCITT,
   transparency additionally requires registering a Signed Statement
   that names the receipt and verifying the resulting SCITT Receipt
   (Section 5).

   Other parties will want to refer to a receipt from the envelopes they
   already use: a DSSE envelope, an in-toto Statement, a SLSA
   Verification Summary, or a SCITT Signed Statement.  This document is
   the third part of one line of work: [STATEMENT-ID] asks how a signed
   statement is named unambiguously, [RECEIPTS] fixes the bytes of a
   receipt, and this document shows how existing envelopes cite such a
   receipt by digest.

   It states how three formats for records of agent actions can cite a
   receipt (Section 6), relates a receipt to a criteria set fixed before
   the run in PRML [PRML] (Section 7), and says where it meets the
   requirements of [ABAK] for exchanging evaluation evidence
   (Section 8).

   This document defines no second receipt format, no new in-toto
   predicate and no new COSE header parameter.  What a receipt does not
   prove stays unproven when an envelope cites it (Section 9).

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in BCP
   14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   The terms receipt, B, Issuer, Receiver and type are used as in
   [RECEIPTS].  The type is the fixed string

   application/vnd.signed-evidence.eval-receipt+json

   The type identifies B ([RECEIPTS] Section 10.1).  The receipt object
   uses the same fixed string as its schema discriminator, but is a
   different JSON representation.

   Receipt digest:  SHA-256 over B (Section 3).

   Citation:  A hash algorithm and a digest value that an envelope
      carries to name a receipt.

   Citing envelope:  An in-toto Statement or a COSE Signed Statement
      that carries a citation.  A DSSE envelope carries B itself, not a
      citation (Section 4.1).

3.  The Receipt Digest

3.1.  Definition

   The receipt digest is SHA-256 over B, the payload bytes of the
   receipt as defined in [RECEIPTS] Section 3.4: the bytes that steps 1
   to 3 of [RECEIPTS] Section 5 obtain from payload_b64.  A candidate
   for which one of those steps fails has no B, even if a lenient
   decoder would produce bytes from it (cases C6 and C7).  It is not
   computed over the receipt bytes or over PAE(type, B).  An envelope
   that carries the digest as text uses the text form that step 1 of
   Section 3.3 fixes for its carrier; one that carries it as bytes uses
   the 32 bytes.  This document defines no other hash algorithm.

3.2.  Why B

   The digest runs over B for two reasons.

   *  B is what is signed.  The signing input PAE(type, B) depends on B
      alone, because the type is fixed ([RECEIPTS] Section 4.2).  A
      digest over B therefore names exactly the signed content; a digest
      over the signing input would carry no further information.



Gruszka                   Expires 29 April 2027                 [Page 4]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   *  The receipt bytes are not stable.  The receipt object around B is
      not canonicalized, and its key hint is not signed.  Vectors P1, P4
      and P6 of [RECEIPTS] are three different receipt byte strings that
      all verify and all carry the same B (cases C1 to C3 of Table 1).
      A digest over the receipt bytes would give one signed statement
      three names, and it would change whenever the receipt object is
      written again.  In-toto resource descriptors and the COSE Hash
      Envelope each name content by the digest of its bytes, and a DSSE
      envelope carries the bytes themselves.

   The price of this choice: the receipt digest identifies the signed
   content, not the signature and not the key.  Two receipts with the
   same B under different keys have the same digest.  The iss and kid of
   a citing Signed Statement (Section 5.2) identify its signer, which
   need not be the receipt signer.  This mapping does not encode a
   constraint on the receipt signer.  A Receiver verifies the cited
   receipt under the receipt key it fixed independently.

3.3.  Matching Rule

   Given a citation and a candidate receipt, the result is computed as
   follows.  For the JSON representation in Section 5.1, first apply
   that section's extraction rule; it either gives INDETERMINATE or
   supplies the algorithm and value for the steps below.  The matching
   result is independent of the typed reference's processing state.

   1.  If the citation's algorithm is not SHA-256, or its value is not
       32 bytes in the form that its carrier fixes, the result is
       INDETERMINATE.  SHA-256 is named sha256 as the key of an in-toto
       digest set [INTOTO-DIGESTSET], -16 as the value of COSE header
       parameter 258, and sha-256 as the algorithm label of the examples
       (Appendix A); each name counts only in its own carrier, and names
       are compared exactly, so SHA256 is none of them.  A typed digest
       reference names it SHA-256 (Section 5.1), an evidence descriptor
       of [EQR] names it sha-256 in hash_alg (Section 6.2), and in an
       ExternalRef of [AIR], which carries no algorithm, the type as
       ref_type names it (Section 6.3).  The value is 64 lowercase
       hexadecimal digits in text form in a digest set (Section 4.3), in
       a typed digest reference (Section 5.1), in an ExternalRef
       (Section 6.3) and in the examples (Appendix A.2); it is the
       base64url encoding without padding of Section 5 of [RFC4648], 43
       characters, in an evidence descriptor (Section 6.2), and a string
       that is not exactly that encoding of 32 bytes is not such a
       value; and it is 32 bytes as the payload of a statement whose
       parameter 258 is -16 (Section 5.2).  A digest set with several
       entries is matched on its sha256 entry alone; this document does
       not judge the other entries.  This is narrower than the matching
       guidance of [INTOTO-DIGESTSET], under which two digest sets match

       if any acceptable field matches: here a digest set without a
       sha256 entry gives INDETERMINATE, and one whose sha256 entry
       passes step 1 but differs from SHA-256 over B gives NO_MATCH,

   2.  If steps 1 through 3 of [RECEIPTS] Section 5 do not all complete
       successfully, including when processing stops at a resource

   3.  Otherwise the result is MATCH when SHA-256 over B equals the

3.4.  Against the Identification Requirements

   [STATEMENT-ID] proposes requirements A1 to A5 for references to
   signed statements.  This section checks the receipt digest against
   them.  It is the author's analysis, not a conformance claim.

   A1, unambiguous target and matching rule:  The scheme names the hash
      algorithm (SHA-256), the input bytes (B, as steps 1 to 3 of
      [RECEIPTS] Section 5 obtain it from payload_b64) and the encoding
      (the text form that step 1 of Section 3.3 fixes for each carrier,
      or 32 bytes).  Section 3.3 is the matching rule.  An unsupported
      algorithm or a candidate without B gives INDETERMINATE, never
      MATCH (C6 to C8).  Identity is preserved under every difference
      outside B that leaves steps 1 to 3 of [RECEIPTS] Section 5
      succeeding: the receipt's whitespace and escapes, its key hint,
      and its signature value.  In the terms of [STATEMENT-ID] Section 5
      the receipt digest is a digest of the payload.  Because the type
      is fixed and nothing else enters the signature, it also determines
      the signing input; neither names the signer.

   A2, readable without interpreting the carrier's payload:  In the COSE
      Hash Envelope of Section 5.2 the citation is read from header
      parameters 258 and 259 and the payload, as [RFC9995] defines them,
      without interpreting application content.  In an in-toto Statement
      the citation lies inside the predicate, which is the Statement's
      application content; a reader has to know the predicate to find
      it.  A2 is met by the first and not by the second.



Gruszka                   Expires 29 April 2027                 [Page 7]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   A3, matching independent of registration:  B does not change when the
      receipt is registered anywhere or its object is written again.
      Cases C2 and C3 carry other receipt bytes and still match.

   A4, acceptance test for A3:  Cases C2 and C3 apply local changes that
      a re-encoding may cause (another JSON escape, a key hint left
      out), and the result stays MATCH.  This is not a measurement of
      registration in two services.

   A5, receipt-verification dependency:  Matching does not depend on a
      leaf hash or a COSE Receipt.  A receipt has no inclusion proof of
      its own; a Transparency Service that registers a statement naming
      it fixes its own leaf construction, and matching does not use it.

4.1.  DSSE

   The signature of a receipt is a valid DSSE signature without any new
   signature.  DSSE [DSSE] signs PAE(payloadType, payload) with the same
   pre-authentication encoding that [RECEIPTS] Section 4.1 defines.  The
   envelope

   {"payloadType": <type>, "payload": <base64 of B>,
    "signatures": [{"sig": <the receipt's signature.sig>}]}







Gruszka                   Expires 29 April 2027                [Page 10]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   therefore verifies as DSSE under the Issuer's key when payloadType is
   exactly the type and payload decodes to B.  Vector M1 (Appendix A)
   gives the bytes; its signature is the signature of vector P1 of
   [RECEIPTS], byte for byte.  M1 leaves out keyid, which DSSE treats as
   an optional, unauthenticated hint.

   A successful DSSE signature check alone is not a receipt verdict.
   DSSE also requires a supported payloadType and parsing the
   authenticated payload according to that type.  To obtain a receipt
   verdict, a Receiver decodes the payload and the selected signature
   once, uses those same bytes to construct the receipt object with
   canonical base64 as required by [RECEIPTS] Section 3.1, and runs
   [RECEIPTS] Section 5 under its independently selected receipt
   verification key.

   The signature is expected to be valid as DSSE only under this
   payloadType, because Ed25519 binds the exact signing input; this is
   not measured beyond sample types.  Vector N7 of [RECEIPTS] shows the
   converse for the receipt itself: its signature, made over PAE with
   the type application/vnd.example.other+json, fails under the fixed
   type.

4.2.  in-toto Statement with test-result

   The test-result predicate [TEST-RESULT] records result (PASSED,
   WARNED or FAILED), configuration (a required list of resource
   descriptors), url, and the lists passedTests, warnedTests and
   failedTests.  A Statement [INTOTO-STATEMENT] that restates a receipt
   maps passed to result PASSED or FAILED.  No member of the predicate
   carries the metric, the comparator, the threshold, the score, the
   sample count or the timestamp; passedTests and failedTests are lists
   of test names, not a count.  The Statement's subject names the tested
   artifact by digest; a commitment is not a digest of the artifact's
   bytes, so the model commitment cannot stand as subject without
   changing what subject means.

   Such a Statement is a new statement by whoever signs its envelope
   [INTOTO-ENVELOPE].  It does not carry the receipt's signature and the
   predicate has no member for the evidence a result rests on.  This
   document therefore does not cite receipts from test-result; the
   mapping states what a party loses when it restates a receipt in that
   form.

4.3.  SLSA Verification Summary

   A Verification Summary Attestation [VSA] states that a verifier
   verified an artifact against a policy.  Its inputAttestations is a
   list of resource descriptors [INTOTO-RD], each of which carries a
   digest of the attestation it names.  A verifier that used a receipt
   as evidence when it verified an artifact, for example the evaluated
   model, and verified the receipt under [RECEIPTS] Section 5, cites the
   receipt there; the artifact itself is the VSA's subject:

   {"digest": {"sha256": "<receipt digest, 64 hex digits>"},
    "mediaType": "application/vnd.signed-evidence.eval-receipt+json"}

   The mediaType identifies B. verificationResult is the verifier's
   result under its policy, not the receipt's passed: a receipt that
   verifies and records passed false (vector P2 of [RECEIPTS]) can be
   the input of a VSA whose verificationResult is PASSED, when the
   verifier's policy asks only for a valid receipt.

5.  COSE and SCITT

   A Signed Evaluation Receipt is not a COSE Receipt.  Its format is
   JSON with Ed25519 over PAE, not COSE; it carries no inclusion proof,
   and no Transparency Service or Registration Policy [RFC9943] takes
   part in making it.  In SCITT, a Transparency Service registers a
   Signed Statement and returns a COSE Receipt [RFC9942] proving its
   inclusion.

   Two existing constructions carry the receipt digest without a new
   field: a typed digest reference (Section 5.1) and a Signed Statement
   whose payload is the digest (Section 5.2).  Both name the receipt;
   neither carries it.

5.1.  A Typed Digest Reference

   [CPB] Section 9 defines a typed digest reference with the members
   type, purpose, digest_alg and digest, and leaves the declaration of
   artifact types to the profiles that accept them ([CPB] Section 9.1).
   This document declares one artifact type for the receipt digest:

   *  type is application/vnd.signed-evidence.eval-receipt+json, the
      type, which identifies B;

   *  there is one digest context, so purpose is absent;

   *  the context has no purpose label, so a well-formed reference that
      carries purpose is Unresolved ([CPB] Section 9.1);




Gruszka                   Expires 29 April 2027                [Page 12]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   *  the canonicalization algorithm is as-transmitted ([CPB]
      Section 5.4), with the byte-boundary selector [RECEIPTS]
      Section 3.4, "The Bytes B";

   *  the pre-image is B as Section 3.1 defines it, the bytes that steps
      1 to 3 of [RECEIPTS] Section 5 obtain, with no exclusion set, no
      further encoding and no domain separation;

   *  the hash function is SHA-256, and digest_alg is exactly SHA-256;

   *  digest is the receipt digest as its 64 lowercase hexadecimal
      digits, a text value; in the cpb-refs header parameter of [CPB]
      Section 9.3 it is a text string.

   For the JSON representation defined here and used in Appendix A.7, a
   reference is one JSON object [RFC8259] with the required members
   type, digest_alg and digest, and the optional member purpose.  Each
   of these members, when present, has a JSON string value.  No other
   member is allowed.  Member names of this object are compared after
   JSON string unescaping, without case folding or Unicode
   normalization; repeated names are detected before any conversion that
   could discard them.  Input that violates the JSON grammar, is not an
   object, has a repeated member name, lacks a required member, has a
   non-string value for one of the named members, or has another member
   is Malformed ([CPB] Section 4).  A byte order mark before the JSON
   text is not part of the JSON grammar, so such input is Malformed,
   although [RFC8259] Section 8.1 allows a parser to ignore it.  Input
   that is not UTF-8 is Malformed as well ([RFC8259] Section 8.1); no
   replacement character is substituted before this check.  This form
   check precedes reference resolution and verification.  The rules
   assigning Unresolved, Failed or Verified apply only to well-formed
   references.  These form requirements define this JSON representation;
   they do not replace the rules for cpb-refs or another profile's own
   serialization.

   For this JSON representation, the independent matching result of
   Section 3.3 is INDETERMINATE unless the input is UTF-8, conforms to
   the JSON grammar, its top-level value is an object, and that object
   contains exactly one digest_alg member and exactly one digest member,
   both with string values.  Otherwise Section 3.3 applies to those two
   values regardless of the reference state.  No occurrence is chosen
   from repeated digest_alg or digest members, even if their values
   agree, and non-string values are not converted to strings.  A
   matching result does not change the reference state or make a
   Malformed reference Verified.






Gruszka                   Expires 29 April 2027                [Page 13]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   A reference under this declaration can stand in the cpb-refs header
   parameter of a Signed Statement, or in a payload that carries
   references in its own serialization, for example in the references of
   [CAPSULE].  For a well-formed reference, context selection and
   verification follow [CPB] Section 9.1.  A well-formed reference whose
   type is not the type of this declaration is not under it; where no
   other declaration that the consuming profile accepts matches it, it
   is Unresolved ([CPB] Section 9.1).  A consuming profile that does not
   name this declaration by normative reference leaves a well-formed
   reference to it Unresolved; no profile names it at the time of
   writing.  Once this digest context has been selected, a digest_alg
   other than SHA-256 or a digest outside the declared text
   representation of 64 lowercase hexadecimal digits makes the reference
   Failed.  Section 3.3 gives INDETERMINATE for either case.  After
   those checks, a verifier that does not implement the construction of
   this context leaves the reference Unresolved (cause: unimplemented),
   whether or not a receipt can be obtained.  A verifier that implements
   it obtains the cited receipt and takes B from it by steps 1 to 3 of
   [RECEIPTS] Section 5.  If no receipt is obtained, the reference is
   Unresolved (cause: unavailable), and the matching result is
   INDETERMINATE, as in step 2 of Section 3.3.  If a receipt is obtained
   and those steps fail, it is not input that the construction of this

   Only the digest crosses, as for the Signed Statement below.  A
   reference that is Verified shows that the cited bytes are B; it does
   not show that the receipt verifies, who signed it, or that its
   assertion is true ([CPB] Section 9.5).

5.2.  A Signed Statement that Cites a Receipt

   A Signed Statement that cites a receipt is a COSE_Sign1 [RFC9052]
   with CBOR tag 18 in the form of a COSE Hash Envelope [RFC9995].  It
   has one of two profiles, which differ in how the statement names its
   signer.  In the key profile, kid names an Ed25519 statement key that
   the Receiver has configured for the issuer.  In the certificate
   profile, the protected header carries an X.509 certificate chain
   [RFC9360] whose last certificate is a trust anchor that the Receiver
   has configured for a did:x509 issuer [DIDX509].  The labels of the
   protected header select the profile (step 2 of Section 5.2.2).



Gruszka                   Expires 29 April 2027                [Page 14]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   Vector M2 (Appendix A) is a statement in the key profile, vector X1
   one in the certificate profile.

   Both profiles share these rules:

   *  The protected header holds exactly the parameters of its profile,
      given below, and no other.  Three of them are the same in both
      profiles:

      -  15 (CWT Claims) [RFC9597]: a map with exactly 1 (iss), whose
         form each profile gives, and 2 (sub), the text value of
         model_id_commit of B;

      -  258 (payload hash algorithm): -16 (SHA-256);

      -  259 (preimage content type): the type, as a text string.

   *  The unprotected header is the empty map.

   *  The payload is the receipt digest, 32 bytes.

   *  The COSE_Sign1, its protected header included, is encoded with the
      core deterministic encoding of [RFC8949] Section 4.2.1.

   Key profile.  The protected header holds exactly the five parameters
   1, 4, 15, 258 and 259:

   *  1 (alg): -19, Ed25519 as fully specified in [RFC9864], or -8,
      EdDSA [RFC9053].  A party that makes a statement MUST write -19.
      A Receiver MUST accept both values and applies every other check
      of Section 5.2.2 to either; under the Ed25519 statement keys that
      step 3 selects, both values select the same signature algorithm.
      Changing alg changes the protected header bytes and requires a new
      signature (Section 5.2.4);

   *  4 (kid): the COSE Key Thumbprint [RFC9679] with SHA-256 of the
      statement key, a byte string of 32 bytes.  For an Ed25519 public
      key x, kid is SHA-256 over the core-deterministically encoded
      COSE_Key map {1: 1, -1: 6, -2: x}; no optional COSE_Key parameter
      enters the thumbprint;

   *  15 (CWT Claims): iss is an absolute URI ([RFC3986] Section 4.3)
      that names the party that makes the statement.

   Its form is fixed, so that one receipt digest, one statement key, one
   issuer and one algorithm value give one byte string.





Gruszka                   Expires 29 April 2027                [Page 15]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   Certificate profile.  The protected header holds exactly the six
   parameters 1, 4, 15, 33, 258 and 259:

   *  1 (alg): -7, ECDSA with SHA-256 ([RFC9053] Section 2.1); the
      signature is r and s, 32 bytes each, under the P-256 public key of
      the leaf certificate (Section 5.2.4);

   *  4 (kid): SHA-256 over the DER encoding of the SubjectPublicKeyInfo
      [RFC5280] of the leaf certificate, a byte string of 32 bytes;

   *  15 (CWT Claims): iss is a did:x509 identifier [DIDX509] that is
      exactly the concatenation of the text did:x509:0:sha256:, F, the
      text ::eku: and O, with no other character, where F is SHA-256
      over the DER bytes of the last certificate of x5chain, encoded in
      base64url without padding (43 characters), and O is an object
      identifier in dotted decimal form: the first arc is 0, 1 or 2, it
      is followed by one or more further arcs, the second arc is at most
      39 when the first arc is 0 or 1, the arcs are separated by full
      stops, and each arc is a decimal number without leading zeros;

   *  33 (x5chain) [RFC9360]: an array of exactly two byte strings, each
      a DER-encoded X.509 certificate [RFC5280]: first the leaf
      certificate, whose P-256 public key verifies the statement
      signature, then the trust anchor certificate, whose RSA public key
      signed the leaf certificate with sha256WithRSAEncryption (RSASSA-
      PKCS1-v1_5 with SHA-256, [RFC8017]).

   This profile names one trust anchor and no intermediate certificate.
   The profile is limited to this form, two certificates with an RSA
   trust anchor, because it is the form measured to work (Section 14).
   An x5chain array with more or fewer than two elements, an x5chain
   that is a single byte string, and an iss with a predicate other than
   one eku give outside_profile in step 2 of Section 5.2.2.  Certificate
   contents, key restrictions and their bindings are checked in step 3,
   which gives untrusted_key when one of those checks fails.  An ECDSA
   signature depends on a per-signature nonce, so one statement in this
   profile can have more than one byte string; the vectors use the
   deterministic nonce of [RFC6979], which a Receiver does not check.

   The value of sub is a choice of this example; the receipt digest does
   not depend on it.  The key that signs a statement and the receipt key
   can be the same key or different keys.  The statement carries its own
   signature over its own Sig_structure; it is not the receipt's
   signature, even when one key makes both.  Registering M2 or X1 with a
   Transparency Service yields a COSE Receipt for that statement, not
   for the evaluation receipt.

5.2.1.  Making a Statement

   A party makes a statement for a receipt only after the receipt has
   passed the verification procedure of [RECEIPTS] Section 5 under a key
   that party fixed.  A receipt that fails it gives no statement.  The
   party computes the receipt digest over B, takes sub from the
   model_id_commit of B, writes the protected header of one profile,
   signs the Sig_structure of [RFC9052] Section 4.4 with an empty
   external_aad, under the statement key in the key profile and under
   the private key of the leaf certificate in the certificate profile,
   and encodes the COSE_Sign1.

5.2.2.  Checking a Statement

   The Receiver holds the statement, a candidate receipt, its
   independently selected receipt verification key, and configured
   pairs.  A pair for the key profile is an issuer URI with an Ed25519
   statement key; a pair for the certificate profile is a did:x509
   identifier with a trust anchor certificate.  The received iss value
   does not establish either association.  It applies the following
   steps in order.  The first step that fails gives the status named in
   it, and the statement is refused; only a statement that passes every
   step is accepted.  A Receiver that stops because it reached a
   resource limit, in any step, reports a resource-limit error; that is
   no status, and the statement is not accepted.

   1.  If the bytes are not one CBOR data item in the deterministic
       encoding, if the item is not a COSE_Sign1, or if its protected
       header is not a map in the deterministic encoding, the status is
       malformed.  A data item that is well-formed but not valid under
       [RFC8949] Section 5.3.1, such as a text string that is not valid
       UTF-8 or a map with duplicate keys, is malformed; two keys are
       duplicates only when they are equal under the key equivalence of
       [RFC8949] Section 5.6.1, so the integer 1 and true are two keys
       and 0.0 and -0.0 are one.  For the choices that [RFC8949]
       Section 4.2.2 leaves to a protocol, step 1 uses these: a NaN is
       in the deterministic encoding only as the half-precision quiet
       NaN 0xf97e00, and any other encoding of a NaN is malformed; no
       tag, the bignum tags 2 and 3 included, adds a rule of its own.
       Step 1 does not check whether the content of a tag inside the
       COSE_Sign1 is valid for that tag ([RFC8949] Section 5.3.2); the
       data items inside a tag are checked like any other data item.
       For step 1, the COSE_Sign1 check concerns only the outer tag, the
       four-element array and its element types: a wrapping in a CBOR
       tag other than 18 is not a COSE_Sign1 and is malformed, and an
       otherwise valid COSE_Sign1 without a tag goes on to step 2 and is
       outside_profile there.  The protected-header byte string is
       decoded as a CBOR map, with the empty byte string treated as an



Gruszka                   Expires 29 April 2027                [Page 17]

Internet-Draft         Evaluation Receipt Mappings          October 2026


       empty map ([RFC9052] Section 3), which fails in step 2.  CBOR
       validity and deterministic encoding are checked before step 2.
       Header label types are checked only in step 2; a header label
       that is not a label of either profile gives outside_profile if
       step 1 succeeds.

   2.  A Transparent Statement [RFC9943] carries COSE Receipts [RFC9942]
       in its unprotected header under label 394.  If the unprotected
       header holds label 394 and no other label, and the value of 394
       is an array of one or more byte strings, the Receiver removes
       label 394 and applies the rest of this step and the following
       steps with the empty unprotected header; the protected header,
       the payload and the signature stay as they are.  These steps do
       not read the receipts.

       The labels of the protected header select the profile: exactly
       the integer labels 1, 4, 15, 258 and 259 select the key profile,
       and exactly the integer labels 1, 4, 15, 33, 258 and 259 select
       the certificate profile.  If the item is not tagged 18, the
       unprotected header is not empty, or the labels select neither
       profile, the status is outside_profile.

       In both profiles, kid is a byte string of 32 bytes; 15 is a map
       with exactly the integer labels 1 (iss) and 2 (sub), both text
       strings; 258 is the integer -16; and 259 is the type as a text
       string.  In the key profile, alg is the integer -19 or -8, and
       iss is an absolute URI.  In the certificate profile, alg is the
       integer -7, iss has the syntactic form given in Section 5.2, and
       x5chain is an array of exactly two byte strings.  This step
       checks only the syntax of iss and the container form of x5chain;
       the certificate contents, key properties, and the bindings of iss
       and kid are checked in step 3.  A violation of these structural
       rules, a detached payload, a payload that is not 32 bytes, or a
       signature that is not 64 bytes gives outside_profile. sub MUST
       match sha256: followed by exactly 64 lowercase hexadecimal
       digits; otherwise the status is outside_profile.  Step 7 compares
       sub byte for byte with model_id_commit of B.

   3.  Key profile.  A configured pair counts only if its statement key
       is 32 octets and its point A meets rules 1 and 2 of [RECEIPTS]
       Section 4.4: A is a canonical encoding of a point of order L.  A
       point of small order or of mixed order does not count.  If no
       configured pair that counts has both an issuer URI exactly equal
       to iss and a statement key whose SHA-256 COSE Key Thumbprint
       equals kid, the status is untrusted_key.  Subsequent signature
       verification uses only keys selected by this pairwise match.





Gruszka                   Expires 29 April 2027                [Page 18]

Internet-Draft         Evaluation Receipt Mappings          October 2026


       Certificate profile.  A configured pair counts only if its
       identifier is exactly equal to iss, its trust anchor certificate
       is byte for byte the second certificate of x5chain, and F of iss
       is SHA-256 over that certificate.  The status is untrusted_key if
       no configured pair counts, or if any of the following does not
       hold: both certificates are DER-encoded X.509 certificates; the
       public key of the trust anchor is an RSA key with a modulus of at
       least 2048 bits; the leaf certificate is signed by that key with
       sha256WithRSAEncryption; the issuer name of the leaf certificate
       is byte for byte the subject name of the trust anchor; the
       extended key usage of the leaf certificate contains O of iss; the
       public key of the leaf certificate is a P-256 key; and kid is
       SHA-256 over its SubjectPublicKeyInfo.  This step is not
       certification path validation ([RFC5280] Section 6) and does not
       resolve iss as a DID: it evaluates no validity period, revocation
       status, name constraint, certificate policy or other extension.
       [DIDX509] requires path validation for resolution.  An
       application that additionally performs path validation reports
       its result separately from the status of this procedure and may
       refuse to use a statement whose status is accepted.

   4.  Key profile.  If the signature does not meet the four rules of
       [RECEIPTS] Section 4.4 under a key that step 3 selected, with the
       Sig_structure of [RFC9052] Section 4.4 in place of PAE(type, B)
       in rule 4, the status is signature_invalid.

       Certificate profile.  Read r and s as unsigned big-endian
       integers from the first and the last 32 bytes of the signature.
       If r or s is not in the range 1 to n-1, where n is the order of
       the P-256 base point, or the signature is not a valid ECDSA
       signature with SHA-256 over the Sig_structure under the public
       key of the leaf certificate, the status is signature_invalid.

   5.  Run the verification procedure of [RECEIPTS] Section 5 under the
       Receiver's receipt key.  Continue to step 6 only if it returns
       PASS.  If it returns FAIL, the status is receipt_not_verified.
       If it stops with a resource-limit error, or with the input error
       of [RECEIPTS] Section 5 because the receipt key is not 32 octets,
       propagate that error and stop without accepting the statement.

   6.  If the payload is not the receipt digest of the candidate, the
       status is digest_mismatch.

   7.  If sub is not the model_id_commit of B, the status is
       subject_mismatch.

   If every step passes, the status is accepted.  Vector M2 with vector
   P1 of [RECEIPTS] is accepted, and Appendix A.6 gives a statement for
   each other status.  Vector X1 with P1 is accepted under the
   certificate pair of Appendix A.8, and X2 to X6 fail at steps 2, 3 and
   4 in the certificate profile.  Vectors T1 to T5 (Appendix A.9) are
   Transparent Statements: T1 and T2 are accepted, and T3 to T5, whose
   unprotected headers hold more than the receipts or the receipts in

   Steps 1 to 4 do not use the receipt.  For the key profile, a general
   COSE verifier that implements the statement's alg value checks the
   signature under the rules of its own Ed25519 implementation, which
   can accept a signature that step 4 refuses, for example one whose R
   is a point of small order.  For either profile, a COSE signature
   check alone does not apply steps 5 to 7, and its success does not

5.2.4.  Choice of alg

   In the key profile, value -19 is the fully specified Ed25519
   identifier of [RFC9864], which sets the polymorphic EdDSA identifier
   -8 of [RFC9053] to Deprecated.  A party that makes a statement
   therefore writes -19 only.  Every Receiver accepts -8 as well, for
   statements made before a producer moved to -19 and for general COSE
   verifiers that implement -8 but not -19 (Section 14), so that one
   statement gives one status. -8 names EdDSA for any curve; step 3 of
   Section 5.2.2 counts only Ed25519 statement keys, so a statement with
   -8 under any other key is untrusted_key.  Vector S1 (Appendix A.6) is
   M2 with alg -8, signed again under the same key; it is accepted.

   The certificate profile fixes -7.  [RFC9864] also sets -7 to
   Deprecated and registers -9 (ESP256) for ECDSA with SHA-256 on P-256.
   The certificate profile does not admit -9: the Transparency Service
   measured in Section 14 refuses a statement with -9 at registration,
   also when its configuration names ESP256, and neither the offline
   verifier nor the two general COSE libraries named there implement -9.
   A statement with -9 is outside the certificate profile (vector X2).
   -7 does not name a curve; step 3 counts only a P-256 leaf key, so -7
   selects one signature algorithm here.

   The payload follows the pattern of the hash-only mode of
   [PRML-PROFILE]: the 32 raw octets of a SHA-256, carried as a byte
   string and not as hexadecimal text.  That profile leaves open how a
   verifier tells such a payload from a full one, and names a COSE
   header parameter that declares the digest algorithm as one candidate.
   Header parameters 258 and 259 of [RFC9995], used here, are such a
   declaration.

6.1.  Control Delivery Evidence

   [ACDE] (revision -02) states evidence requirements for the delivery
   of control instructions, such as stop or suspend, to enforcement
   points.  It defines a logical evidence model and no wire format; its
   illustrative record is, in its own words, "deliberately not a wire
   format".  Every observation used to correlate an instruction binds
   the instruction identifier to a digest of either the exact
   instruction or a declared canonical projection of it, and the
   applicable protocol or profile identifies the projection, the digest
   algorithm, the canonicalization rule and the domain-separation rule,
   if any (its Section 5.2, R-CD-2).  Records within one declared
   identity-uniqueness scope that reuse one instruction identity with
   different governed content are SUBSTITUTION, also between issuer and
   receiver records (its Section 6.1).

   A receipt that motivates a control can therefore be cited inside the
   governed instruction: an instruction whose exact bytes contain a
   typed digest reference to the receipt (Section 5.1) carries the
   citation, and every observation that binds the digest of those bytes
   binds the citation with them.  An observation that binds the digest

6.2.  Evidence Qualification Receipts

   [EQR] (revision -00) defines the Evidence Qualification Receipt
   (EQR), a JSON object that binds a proposition to a versioned evidence
   profile and lists evidence descriptors.  Each descriptor binds at
   least a digest and an evidence class; sha-256 is the mandatory-to-
   implement digest algorithm, and digest values are base64url without
   padding (its Section 5).  Its Section 5 also says that an
   implementation that computes a digest over a JSON payload should use
   [RFC8785] before hashing, and that the applicable profile defines the
   bytes hashed for an object that is not JSON.

   An EQR cites a receipt with one evidence descriptor, written with the
   member names of the example in its Section 5.2: class is the type,
   hash_alg is sha-256, and digest is the receipt digest in base64url
   without padding.  B is in the serialization of [RFC8785] (step 5 of
   [RECEIPTS] Section 5), so its RFC 8785 bytes are B itself and the
   digest over them is the receipt digest.  The bytes cited are B, not
   the receipt object (Section 3.2); an EQR profile that admits receipts
   as evidence is where that choice would be stated.

   Matching applies Section 3.3 to hash_alg and digest of the
   descriptor.  An EQR that is valid under Section 8 of [EQR] and
   qualifies under its Section 8.1 shows nothing about the cited
   receipt, and the two results stay apart.

   Open in [EQR] -00, and not assumed here:

   *  a vocabulary of evidence classes, and whether the local trust
      policy of step 7 of its Section 8 accepts the type as a class;

   *  the member names of an evidence descriptor, which appear only in
      its example (the vectors use class, hash_alg and digest);

   *  the format of an evidence profile, which it does not define (the
      vectors use a JSON object of their own);

   *  how a profile states which bytes of a cited object are hashed;

   *  local metadata such as a retrieval reference for the receipt,
      which it leaves to deployments.

6.3.  Agent Interaction Records

   [AIR] (revision -01) defines the AgentInteractionRecord (AIR), the

7.  Criteria Sets in PRML

   A Receiver that holds a receipt and a PRML manifest compares them as
   follows and reports the two results separately.

   1.  Run the procedure of [RECEIPTS] Section 5 under the Receiver's
       receipt key.  Continue only if it returns PASS.  If it returns
       FAIL, do not perform the comparison.  If it stops with a
       resource-limit error, or with the input error of [RECEIPTS]
       Section 5 because the receipt key is not 32 octets, propagate
       that error and stop without reporting binding or agreement
       results.

   2.  The manifest is canonicalized as [PRML] Section 3 requires, and
       its manifest hash is computed.  A manifest that PRML rejects is
       not compared.

       criteria_digest and it equals sha256: followed by the manifest
       hash, and UNBOUND otherwise.

       both, comparator is the same and is not ==, and the receipt's
       threshold and the manifest's threshold are the same decimal

       canonical rendering denotes (so 0.8 in the manifest and 0.800 in
       the receipt agree, and 0.80000000000000001 in the receipt does
       not).  Otherwise it is DIFFER.

   manifest; AGREE says that the two documents state the same metric,
   comparator and threshold.  Neither result shows that the manifest
   existed before the run, which needs a time-anchored record of the

   manifest, such as a registration under [PRML-PROFILE], and evidence
   of when the run began.  Neither shows that the dataset with the
   manifest's content hash was the one evaluated, or that the seed was
   used.

9.  What Is Not Proven

   The list of [RECEIPTS] Section 6 applies unchanged to a cited
   receipt.  It is repeated here word for word; its one cross-reference
   is written as a reference to Section 5 of [RECEIPTS].

   Verification establishes that the receipt passes the format,
   consistency and signature checks in Section 5 of [RECEIPTS] under the
   Receiver's selected key.  PASS does not mean that passed is true or
   that the result meets the Receiver's requirements for its intended
   use.  Establishing who controls that key and whether that party is
   authorized to make the claim is outside this procedure.  Verification
   does not establish that the Issuer's claims are true.  In particular:

   *  The score can be false.  The evaluation can be wrong, badly
      designed or not run at all; the receipt records what the Issuer
      states.

   *  The run need not have been the only run.  An Issuer can evaluate
      many times and record only the run it prefers.

   *  The Issuer can lie.  A valid signature binds the statement to the
      key, not to the truth.

   *  A receipt does not show that it was published, logged or shown to
      anyone else.  A receipt does not prove registration with a
      Transparency Service.  In SCITT, transparency additionally



Gruszka                   Expires 29 April 2027                [Page 27]

Internet-Draft         Evaluation Receipt Mappings          October 2026


      requires registering a Signed Statement carrying the receipt or
      its digest with a Transparency Service and verifying the resulting
      SCITT Receipt.  Registration and verification of the resulting
      SCITT Receipt are outside this document.

   *  The receipt bytes are not a stable name for the receipt.  Only B
      is signed; the receipt object around it is not canonicalized, and
      its key hint can be present or absent.  A party that cites a
      receipt cites SHA-256 over B.

   *  A commitment is computationally binding under the collision
      resistance of SHA-256.  A Receiver can check a claimed opening
      only after receiving the salt and identifier.  Hiding depends on
      keeping an unpredictable salt secret.

   *  The timestamp is the Issuer's statement, not a time attested by
      another party.

   *  The receipt says nothing about individual samples: n is the
      Issuer's statement, and no sample result is committed or can be
      disclosed against the receipt.  A sample-level audit is outside
      this document and is left to a separate document.

   *  A receipt does not show that the threshold was fixed before the
      run.

   *  criteria_digest binds only the Issuer's statement that this result
      belongs to the criteria set with that digest.  It shows neither
      that the criteria set existed before the run nor that the metric,
      comparator and threshold in it equal those in the receipt.

   *  Even with salt and identifier disclosed, the receipt does not show
      that the named model or dataset was the one actually evaluated.

   *  A receipt does not show where B came from.  B carries no reference
      to another receipt or record that it was made from, for example
      when an Issuer translates the result of another format into a
      receipt; this format has no member for it.

   Each envelope adds what it does not prove:

   *  A citation.  A MATCH does not show that the candidate verifies,
      who signed it, or that its assertion is true (case C5).  The
      digest names B; it names neither a signature nor a key.







Gruszka                   Expires 29 April 2027                [Page 28]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   *  DSSE.  A successful DSSE signature check authenticates PAE(type,
      B) under the selected key.  A receipt verdict additionally
      requires the verification profile and all checks of [RECEIPTS]
      Section 5.  The unauthenticated keyid is only a key-selection
      hint.

   *  in-toto test-result.  A Statement that restates a receipt is the
      statement of its signer.  It does not show that a receipt exists,
      and its result does not show that the receipt's passed is true;
      both are statements.

   *  SLSA VSA.  A VSA shows that its verifier states that it verified
      its subject under its policy, with the cited receipt among its
      inputs. verificationResult is not passed, and the VSA does not
      make the receipt's assertion true.  The digest in
      inputAttestations names B, not the signature or the key the
      verifier used.

   *  SCITT Signed Statement and COSE Receipt.  The Hash Envelope
      carries only the digest.  Its registration shows that a
      Transparency Service registered a statement naming that digest
      under its Registration Policy.  It does not show that a receipt
      with that B exists or that it verifies, and sub binds nothing
      beyond the commitment it repeats.

   *  Typed digest reference.  A Verified reference shows that the cited
      bytes are B, nothing about the signature, the key or the
      assertion.  A MATCH alone does not establish that the reference is
      well formed or that its digest context has been resolved.

   *  PRML.  BOUND and AGREE (Section 7) do not show that the criteria
      were fixed before the run.

   No envelope in this document carries sample data: a receipt commits
   to no sample result ([RECEIPTS] Section 6), and a citation names only
   B.

10.  Related Work

   [FRAMING-SPACE] measures the CBOR framing space of one COSE_Sign1
   object under six encoding freedoms: with or without tag 18, definite
   or indefinite length for the outer array and for the unprotected
   header map, and whole or chunked byte strings for the protected
   header, the payload and the signature.  It reports 64 distinct octet
   sequences that share one Sig_structure, and so one signature, while
   each has its own digest over the transmitted octets.  It notes that
   the core deterministic encoding of [RFC8949] Section 4.2.1 excludes
   five of these freedoms and leaves the choice between the tagged and



Gruszka                   Expires 29 April 2027                [Page 29]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   the untagged form.

   The Signed Statement of Section 5.2 is restricted in both respects:
   the whole COSE_Sign1, its protected header included, is in the core
   deterministic encoding, and step 2 of Section 5.2.2 requires tag 18.
   For a statement whose header contents, payload and signature bytes
   are fixed, one of the 64 combinations therefore remains.  A digest
   over the transmitted octets and a digest over the Sig_structure still
   identify different objects: in the certificate profile one statement
   can have more than one byte string (Section 5.2), each with its own
   digest over the transmitted octets and all with one Sig_structure.
   This document names a receipt by the digest of B (Section 3) and
   defines no identifier for a statement that cites it.

11.  Security Considerations

   This section follows the guidance of [RFC3552].  The attacker can
   read, create, modify, replay and reorder receipts and citing
   envelopes, and controls every input except the Receiver's choice of
   verification key.

   Collisions.  A citation names B only as well as SHA-256 resists
   collisions and second preimages.

   Signer not bound.  The receipt digest does not name a key.  An
   attacker who signs the same B with its own key produces a receipt
   that matches every citation of B.  It fails verification under the
   Receiver's key (Section 3.2).

   Signature reuse across envelopes.  By design the signature of a
   receipt is a valid DSSE signature under payloadType equal to the type
   (Section 4.1).  A DSSE consumer that accepts that payloadType holds
   the B and the signature of a receipt, and applies [RECEIPTS]
   Section 5 before it relies on them.  Under any other payloadType the
   signature is expected to be invalid (Section 4.1).  It is not a COSE
   signature, because COSE signs a Sig_structure and not PAE.

   Digest confusion.  For one receipt, the receipt digest, the SHA-256
   of the receipt bytes and the SHA-256 of a DSSE envelope are three
   different values.  A Receiver compares only the receipt digest with a
   citation.  Appendix A lists the first two for vector P1 and the third
   for M1.  The type identifies B, but a receipt object carries the same
   string as its schema: a Receiver that fetches a receipt object for a
   citation takes B from it by steps 1 to 3 of [RECEIPTS] Section 5 and
   compares the digest of that B, never the digest of the object.






Gruszka                   Expires 29 April 2027                [Page 30]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   Algorithm.  Only SHA-256 is defined.  A citation with another
   algorithm gives INDETERMINATE (case C8), so it cannot be satisfied by
   a weaker digest.

   Reference parsing.  For the JSON representation in Section 5.1,
   duplicate detection precedes any conversion that could discard member
   names.  Selecting a first or last occurrence can change the reference
   state or matching result.  A MATCH is not a substitute for Verified:
   a Malformed, Unresolved or Failed reference is not relied on as
   evidence of a content binding ([CPB] Section 9.1), and neither is a
   reference whose processing stopped at a resource limit.

   Receipts not read.  Step 2 of Section 5.2.2 removes the receipts of a
   Transparent Statement without reading them; vector T1 carries a
   receipt made for another statement and is accepted.  An accepted
   status therefore says nothing about registration.  A Receiver that
   relies on registration verifies each receipt under [RFC9942] with a
   Transparency Service key that it fixed itself.  It fixes the key, not
   the issuer name in the receipt: two instances of a Transparency
   Service can carry the same issuer name and differ only in their keys
   (Section 14).

   Digest not checked by registration alone.  The Signed Statement
   carries a digest, not B.  Registration under a Transparency Service's
   policy does not by itself establish that the payload equals SHA-256
   over B; Section 14 records the registration of a statement whose
   payload was not that digest.  The Receiver recomputes the receipt
   digest in step 6 of Section 5.2.2.

   Configured trust.  A Receiver trusts a statement key or a trust
   anchor because it configured it.  In the certificate profile, the
   procedure checks the leaf under the configured anchor but evaluates
   no validity period or revocation status.  A compromised leaf key can
   therefore continue to pass this procedure while the configured pair
   remains.  Additional path validation or other acceptance policy can
   refuse its use separately.  Removing a configured pair makes
   statements that would pass step 2 and whose only matching pair was
   removed fail at step 3 with untrusted_key.

12.  Privacy Considerations

   The receipt digest lets anyone who holds a candidate B confirm it.  B
   carries salted commitments, so B cannot be guessed without them; a
   party that knows them can test guesses for the remaining members,
   such as score and threshold.  A citation registered with a
   Transparency Service publishes the digest for as long as that service
   keeps its log.  The sub of M2 repeats the model commitment of B in
   clear; registered, it links every receipt and statement that commit



Gruszka                   Expires 29 April 2027                [Page 31]

Internet-Draft         Evaluation Receipt Mappings          October 2026


   to the same model identifier with the same salt ([RECEIPTS]
   Section 9).  The same holds for a criteria_digest that a receipt
   carries.
